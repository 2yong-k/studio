# studio — image and video workshop
Status: in use
Date: 2026-10-29

Reply in the user's language.

When the user asks in plain words, finish the design (the brief) by asking questions, check it with no money spent using shapes and a rough drawn video, then get an estimate approved and generate everything to fit in one pass.
Generation, approval and spend all go through the single command `studio <command>`. The rules in this document come first, before anything the code blocks.

## Before you start
- Run the CLI as **`node "${CLAUDE_PLUGIN_ROOT}/studio.mjs" <command>`**; live: **`node "${CLAUDE_PLUGIN_ROOT}/studio.mjs" --live <command>`**. It is the same line in Bash and PowerShell, from any folder (a bare `node` is command mode and needs no `&`). A bare `studio` may start another program of that name (Android Studio's launcher is one), which is why the full line is used. These documents write it `studio <command>` and `studio --live <command>` for short.
- Writing a command line: put every path in double quotes, and write a Windows path as `C:/…` (with its drive, and `/` as the separator). Put `--reason` text in double quotes with no `$`, backtick or `"` inside it. Never put JSON on the command line: write it to a file with the Write tool (`price-check --stated-file`, `references/estimate.md`).
- The first time this skill is used in a session, run `studio doctor` before anything else ("First run" below).
- This skill's folder is `${CLAUDE_SKILL_DIR}`. Read the reference documents at `${CLAUDE_SKILL_DIR}/references/<file>` (written `references/<file>` in these documents). The plugin folder is `${CLAUDE_PLUGIN_ROOT}`, and the bundled model list is `${CLAUDE_PLUGIN_ROOT}/data/models.json` (written `data/models.json`). Never edit anything in the plugin folder — every update replaces it.
- The user's own files live in the studio folder: the `home` that `studio doctor` returns (written `<home>` in these documents). It holds the works (`works-fake/`, `works/`), `assets/`, the page-price records (`price-checks.json`) and the prompt lessons (`lessons.md`) — `references/setup.md`.
- The hard rules below apply whatever folder the session was opened in.
- In the `<work>` slot of a command, write the work folder name (`2026-10-30-pilot`), not a path.
- `sheet` and `speech`, which take a file path, accept **absolute paths** only (a relative path gives `USAGE`; on Windows a path without its drive, such as `/c/work/…` or `\work`, gives `USAGE` too, so write `C:/…`). The paths other commands return (`video`, `frames`, `file`, `sheets`) are absolute, so use them as they are. On Windows the output writes non-ASCII letters as `\uXXXX` escapes (a user folder with an accented or Korean name, for example): decode them as a JSON parser does before writing a returned path on a command line or in a file. `results[].file` returned by `generate` is relative to the work folder, so join it as `<absolute path of the work folder>/<file>` (the work folder path is the `dir` that `new` returned). If the session continued and you lost `dir`, the work folder is `<home>/works-fake/<work>` (fake mode; with `STUDIO_WORKS_ROOT`, `<that path>/<work>`) or `<home>/works/<work>` (`--live`). The `video` and `frames` that `preview` returns are inside `<work folder>/preview/` and the `file` from `make` is inside `<work folder>/build/`, so you can work the path back from those too.

## First run
Run `studio doctor` once at the start of a session. It spends nothing, makes no network call, and checks only whether a key is stored, never its value. The output has `home` (the studio folder) and `checks[]`, one `{ id, ok, detail }` each for `node`, `ffmpeg`, `home`, `key` and `voices`. Show the user the `home` path in one line, and tell them only about the items with `ok: false`, each with what to do (`references/setup.md`, "What `doctor` checks"); do not list the ones that passed. If `home` is not the studio folder the user chose, stop before any work and point them to `/plugin configure` and a new session. When unsure, ask the user whether it is their studio folder. `node`, `ffmpeg` and `home` are needed for everything. Without `key`, fake mode still works fully — the key is needed only for live mode. Without `voices`, `preview` still works: the lines no voice can read are previewed silently, with timing estimated from the text (`references/preview.md`).
If `doctor` itself fails with `CONFIG_INVALID`, the studio folder is not set or its setting is broken — see that code in the error table below.
Right after install the mode is fake. Live generation happens only after the user approves a live-mode estimate (a fake-mode approval never carries over).

## Flow
Seven steps. If the brief changes after approval, go back to steps 3–4 (approval is tied to the brief and estimate hashes). If you changed the composition (anything drawn into the layout guide PNG: layout, components, cuts, size, and so on), run `preview` again before `estimate` — the guide image sent to the generation model is a file `preview` wrote, and if you do not redraw it, `estimate` and `generate` notice that it differs from what the current brief would draw and refuse with `BRIEF_INVALID` (`reason`: `the layout guide is older than the brief; run preview again`).

| Step | What Claude does | Command | Document to read | Money |
|---|---|---|---|---|
| 1 | Take the request and fill in the brief by asking questions | `new <name> --kind image\|video` | `references/brief.md` | None |
| 2 | Show a rough drawn video (for an image, one shape preview) and fix it — free iterations. For a video work, decide and write the lines, the actions and the scenes | `preview <work>` | `references/preview.md`, `references/scenes.md` | None |
| 3 | Show the estimate and adjust it with "how much if we drop this". In live mode, if a model with a stated price (`billing.stated`) is used, re-check that model's page and record it with `price-check` before the estimate | `price-check <model> --stated-file "<home>/price-check-input.json"` (live mode), `estimate <work>` | `references/estimate.md` | None (price lookups only) |
| 4 | When the user says "approve" in the conversation, record the approval | `approve <work>` | `references/estimate.md` | None |
| 5a | Make the generated image elements and the video keyframes | `generate <work>`, and `status <work>` if it gets stuck | `references/prompting.md` with `<home>/lessons.md`, `references/recovery.md` | **Spent** |
| 5b | Show the keyframes to the user as a contact sheet and record the confirmation | `sheet <absolute path>`, `approve <work> --keyframes` | `references/review.md` | None |
| 5c | Make the video from the confirmed keyframes as first frames | `generate <work>`, and `status <work>` if it gets stuck | `references/recovery.md` | **Spent** |
| 6 | Make the candidate file by drawing and compositing, and review it (match caption times with `speech`) | `make <work>`, `sheet <absolute path>`, `speech <absolute path>` | `references/review.md` | None |
| 7 | Fix a clear defect partially within the margin; when it is ambiguous, show the user a comparison. When the user approves publishing, finish, and write the prompt lessons from this work into `<home>/lessons.md` | `generate <work> --element <id> --reason "<defect>"`, `finish <work>` | `references/review.md` | Within the margin |

An image work has no 5b or 5c (there are no video elements, so no keyframe confirmation either). A video that uses an imported keyframe (`fromFile`) has no 5b and is made directly in `generate` of 5a. So write only a picture the user saw and chose in the conversation in `fromFile`, and never copy an unconfirmed `raw/` result of this or another work into `inputs/` to use it (the code rejects every path outside `assets/` and `inputs/` and every link into `raw/`). `generate` (with no element given) makes only the elements that are not finished, and it does not make a keyframe and the video that uses it in one go — the keyframe confirmation sits between them.

**Run `generate` and `status` with the Bash or PowerShell tool's `run_in_background` and wait for the notification that it finished.** A live-mode video waits up to 20 minutes, and a call run directly in the foreground cannot run that long. If the run was cut off or the output was lost, call `status` first and do not call `generate` again — the cut-off run may already have sent an attempt (hard rule 2).

Other commands: `resolve <work> <attempt> --not-sent | --request-id <id>` (`<attempt>` is the whole value of `results[].attempt` or of `submitting[].attempt` in `status`, for example `2026-10-30-pilot/hero/1`. Only after the user has checked the console and told you about an attempt stuck in `submitting` — `references/recovery.md`), `resolve <work> <attempt> --failed` (only after the user has checked the console and said there is no usable result — it closes as `settled`·`provider_failed` a `sent` attempt that `status` keeps failing to clear (it keeps giving `PROVIDER_ERROR`, `DOWNLOAD_REJECTED` and so on), or a `submitting` attempt the user cannot confirm in the console. It sends nothing, and the estimated amount stays in the spend. After that, `generate` with no element given skips that element with `LAST_ATTEMPT_FAILED`), `smoke` (only as far as the estimate for the cheapest single image — the first check in live mode, only when the user asks for it), `doctor` (the first-run check above), `price-check <model> --stated-file "<home>/price-check-input.json" [--changed]` (records a model's page price, re-checked today, in the studio folder. No money and no network. Claude writes the JSON to that file with the Write tool first, and the file names its `model` — `references/estimate.md`. `--changed` only after the user has confirmed a changed price in the conversation), `price <endpoint…>` (**for the plugin's maintainer only**: it prints the supplier price API's answer `quotes[]` as it is, for adding a model to the bundled list. Users do not add models, so do not use it in a user's work. No money goes out, but it is a network command, so it needs the key in `live`. Up to 50 at a time, more gives `USAGE`), `speech <absolute path>` (from a video or sound file, prints the stretches where there is sound, `segments[]` (`startMs`, `endMs`) — use it to match caption times. It goes by volume, not speech recognition, so loud background sound widens the stretches. If there is no sound track, `USAGE`).

## Hard rules — never do these
1. No generation call without an approved estimate. The default is fake mode. Run `approve` only after the user has approved in the conversation.
2. Never send an attempt that was sent or is unconfirmed again (clear it only with `status`, or with `resolve` after the user has checked the console).
3. Never delete a work folder or an asset binary — no `git clean -x`, no `rm -rf works/`. Only the user deletes.
4. Never look at or write a key value — do not run `security … -w` directly, and never read, search, copy, edit or delete the key file (`provider-key.json` in the studio config folder) or Claude Code's `.credentials.json`. A guard hook refuses common ways of reading either, but it is a speed bump, not a barrier: this rule binds you whatever the hook lets through, so never look for another way to read the key.
5. No model, font or music that cannot be used commercially.
6. No impersonating someone else's brand and no false scenes that look like fact (brands the user owns are the exception). Make a real person's likeness only from a photo of the user or of a person who consented.

One more besides these six: when confidence is low or the judgement is ambiguous, stop and ask the user (no automatic progress).

## Modes
- With no flag it is fake mode. The fake adapter uses no money and no network, and works are made in `<home>/works-fake/`. All practice and checking happen here. A fake image is a flat grey, and a fake video is a test screen (at the model's fps) with a beep of only 0.4–1.6 seconds every 2 seconds, so you can practise everything down to matching caption times with `speech`.
- Use `--live` (`studio --live <command>`) **only for a real work**. The work is made in `<home>/works/` and money goes out. `--live` is accepted only as the first argument, before the command; after the command it gives `USAGE` and nothing runs. The work folder roots of the two modes differ, so a fake work is not visible in live mode — to make it for real, start again from `new`, get a new estimate and get it approved. Every command for one work, even the free `preview`, `sheet` and `make`, runs in the mode that made it — called in the other mode it cannot find the work and gives `NOT_FOUND` (`sheet` gives `USAGE`, because the file is outside that mode's work folder). A live work in progress continues with `studio --live status <work>`, never without the flag.
- Commands that are `live` and need the network (`estimate`, `generate`, `status`, `smoke`, `price`) read the key from its store at the start: the macOS Keychain on macOS; an owner-only file, `provider-key.json` in the studio config folder, on Windows and Linux. The guard refuses the common ways of reading either (a speed bump, not a barrier). If the key is missing, it is `KEY_MISSING` — the user adds the key with `/plugin configure` and starts a new session (`references/setup.md`). Neither look at nor ask for the key value, and never let the user paste it into the chat.
- `STUDIO_MODE` is no longer read. While it is set to any non-empty value, every command refuses to start with `MODE_INVALID`, even with `--live`; the user removes it where it is set and restarts Claude Code (`references/setup.md`, "`STUDIO_MODE` left set").
- Always check which mode you are in with `mode` in the output. Amounts in fake mode are practice values worked out from recorded prices, so say so when you show them to the user.

## Reading command output
- The output is one JSON object on stdout. Success is `{ "ok": true, "mode": …, … }`; failure is `{ "ok": false, "error": { "code", "message", "details" } }` (plus a `cause` string if there is a cause) with exit code 1. An unexpected exception (`UNEXPECTED`) has exit code 2 and the stack goes to stderr — it is a bug in studio, so stop and tell the user (the `message` and the first lines of stderr) so they can report it to the plugin's maintainer. The exception: a `message` starting `EPERM`, `EACCES` or `EROFS` on a path in the studio folder means the folder cannot be written — under Claude Code's sandbox it needs allowing (`references/setup.md`, "Claude Code's sandbox"), otherwise its permissions are wrong (`doctor`'s `home` check). When studio cannot start at all (a Node that is too old, a package that will not load), stdout is empty, stderr is one line starting `studio: ` and the exit code is 2: tell the user that line and what `references/setup.md` ("Install") says to do. The exception is `studio: the command stopped on <signal>`: the command was stopped partway, so run `status` before anything else and send nothing again. On Windows, non-ASCII characters in the JSON come as `\uXXXX` escapes (a user folder with an accented name, for example); they read the same once the JSON is parsed.
- `generate` and `status` can finish with `ok: true` even when an attempt is blocked. **Always look at `results[].error` and `results[].cause`** (`ATTEMPT_UNRESOLVED`, `WAIT_TIMEOUT`, `DOWNLOAD_REJECTED` and so on). `status` also reports, in the `submitting` array, an attempt that stopped without a request id. If you call `generate` again on an element that already has an unconfirmed attempt, it is not `results[].error` but `ATTEMPT_UNRESOLVED` (`details.attempt`) with `ok: false`. If an error comes after one call has already made other elements, the finished results come in `error.details.results[]` — count the money that went out from there.
- `generate` with no element given tells you the next step with `next`: `keyframe_review` means 5b, `make` means step 6, and `nothing` means the unfinished elements are blocked (resolve `results[].error` first). Output from a call with `--element` has no `next`.
- `results[].reason` is the reason for a settled attempt (the model's refusal text, the reason a check caught it, the defect that was remade). `outcome: "refused"` means the supplier refused the input itself — the money is counted at the estimated amount, like `provider_failed`. Do not read `spend.jsonl` to find that reason.
- If `results[]` has `error: "LAST_ATTEMPT_FAILED"`, this call did not send that element. The `outcome`, `amountMicros` (and `file` too if `rejected`) on that line are values of the **earlier attempt**, not money that went out this time — do not add them to the spend. The other elements keep being made.
- Amount fields (`…Micros`, and `spend`, `approved`, `cap`) are integer strings in micro-dollars (1 USD = 1,000,000). For the user, use the `$` values of the `usd` object (`usd.spend`, `usd.approved`, `usd.cap`, and for an estimate `usd.subtotal`, `usd.lines`).
- If `budget: "margin_in_use"` is present, spend has reached the approved subtotal (equal or over). If equal, it finished as estimated and the margin is still intact, and from now on the money for remaking comes out of the margin. If over, that much of the margin has been used. Tell the user which one it is, using `usd`.
- Do not paste the JSON to the user as it is. Summarise it — what was done, how much went out (`$`), and what to do next.
- If `details.file` of `BRIEF_INVALID` is present and is not `brief.json` (a record file such as `spend.jsonl`, `approvals.jsonl` or `estimate.json` is broken), fix nothing, stop, and tell the user. Never edit a `.jsonl` file.
- When an error code appears, follow this table first.

## Making assets
There is no separate command. When a work produces something worth reusing (a hero sheet, a style sentence, a brand kit), ask the user and Claude does it directly.
1. **Copy** the file into `<home>/assets/<name>/` (do not touch the original work folder). A brief points at it as `assets/<name>/…`. If the user keeps the studio folder in git, binaries stay out of git.
2. Write a description text in the same folder — what it is, where it came from and how to use it. In git, commit only the text.
3. For fonts and music, write the license in `<home>/assets/<name>/asset.json`. If it is missing, the brief refuses with `ASSET_LICENSE_MISSING`.
```json
{
  "schema": 1,
  "files": {
    "<path relative to the folder>": {
      "license": { "name": "<license name>", "commercialUse": true, "source": "<source URL>", "checkedAt": "YYYY-MM-DD" }
    }
  }
}
```
Use only what is confirmed `true` for commercial use (hard rule 5). The bundled fonts are used with no record: Pretendard (`pretendard-regular`, `pretendard-bold`), Inter (`inter-regular`) and Instrument Serif (`instrument-serif-regular`). Inter and Instrument Serif have Latin letters only, so Korean text needs Pretendard.
How to use them is in `references/prompting.md`.
